# M01 单一决策权多 Agent 首试评审

日期：2026-08-11

## 结论

`agent-eval-m01-multiagent-v1` 在启用只读证据研究员的工具面下完成了 Lead 运行，但 Lead 没有调用 `task`，因此该运行对专业子 Agent 价值是 **untriggered / 未触发**，不是多 Agent 业务通过或失败。提交前复核还发现，当时嵌入式客户端没有把评测配置副本传入工具运行时；这个缺口已测试先行离线修复，但没有再次付费运行。因此本次 `1/1` 只能表示 Lead 运行技术完成，不能表示真实委派链路已通过。

Lead 最终输出仍然增加了无依据的表现形式、产能、内容供给、引流资产、价格、周期和阈值，因此本轮最终孵化判断继续为 **business-rejected**。ADR-009 保持 `proposed`。

## 实际轨迹

Lead 工具面包含 `task`，且实验 manifest 只允许一个专业子 Agent。实际轨迹为：

1. `incubation_project_context`：成功读取八条当前事实。
2. `incubation_project_evidence`：成功读取一个评测输入证据快照及其局限。
3. `incubation_context`：召回“受众问题”与“最小实验”两张方法卡，其反例明确禁止宝妈标签推断和任意播放/咨询阈值。
4. `task`：`0` 次。

这个路径符合 DeerFlow 的“直接执行默认、只在净收益明显时委派”规则。M01 只有一个小型项目快照，Lead 自读三项工具的路径很短；不应为了让实验看起来像多 Agent 而强制委派。

## 提交前运行时复核

真实运行之后的逐层复核发现，`DeerFlowClient` 虽然用显式 `app_config` 构建 Lead 和渲染专业角色，却没有把同一配置放入工具运行时上下文。`task` 在真正执行时会从该上下文解析子 Agent；在本次运行时版本中，如果 Lead 调用了评测器临时注册的 `incubation-evidence-researcher`，它可能回落到进程默认配置并无法解析该角色。

- 本次轨迹中 `task=0`，因此这个缺口没有改变已记录的模型输出和业务评审。
- 已先增加 `DeerFlowClient` 显式配置传播失败测试，再将同一 `app_config` 绑定到每次嵌入式运行上下文。
- 客户端和子 Agent 离线回归已覆盖该链路。
- 没有用离线修复改写历史运行结论，也没有自动发起第二次付费 trial。

所以当前最准确的状态是：**运行时已离线修复，真实委派仍未验证，M01 业务仍不通过**。

## 业务评审

输出有一个进步：它首先列出了会改变路线的主体未知，包括可公开的案例证明、擅长的小生意领域、可接受的表达形式和服务范围/客单。

但它随后没有保持这些未知，而是直接补齐方案：

- 把“专注小生意低成本避坑”定为起号定位，未验证小生意垂类、付费问题或差异证明。
- 无主体表现、制作速度或历史数据，却声称图文每周 `4-6` 条、语音 PPT 每周 `2` 条、真人口播每周 `1-2` 条，并将真人口播写成“信任度最高”。
- 在没有真实问题库或供给证据时，规定前 `30` 条、四类高频场景、每类 `7-8` 个问题，并假定公开问题库能持续供给。
- 无资产、交付范围和价格依据，却新增免费“财务自查清单”和 `99元` 财务体检。
- 无平台、基线或产能依据，却规定两周 `10` 条图文、单条 `500` 阅读。
- 将“有人询问是否付费”升格为“需求存在”，与它已读到的方法反例直接冲突。
- 又新增本地商家群、创业群和免费 15 分钟答疑的替代路线，但输入中没有这些渠道和履约意愿。

这说明“识别了未知”还不等于“在判断中尊重未知”。当前失败仍发生在 Lead 的业务推理，不能通过强制增加一个子 Agent 来掩盖。

## 对架构的意义

1. DeerFlow 已具备在同一运行时内限制一个只读专业子 Agent 的结构；权限、配置传播和密封合同已离线通过，但本轮真实运行没有验证委派执行。
2. M01 的小型只读对账不会自然产生委派净收益，本轮不能用来测专业子 Agent 的实际输出质量。
3. 不修改 Lead 提示词去强制 `task`；否则只是把第四版的强制工具路线换了一个名字。
4. 若继续评测专业子 Agent，应选择真正证据密集、需要隔离上下文的任务，例如经授权的账号拆解或多来源市场研究，而不是强迫 M01 走一次部门流程。
5. M01 主线仍应解决“在关键未知存在时，Lead 如何停在条件化判断并继续获取主体信息”，而不是增加角色数量。
