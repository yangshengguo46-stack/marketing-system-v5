# A33 账号结构化提取可行性审计

## 结论

`Agent + Skill` 路线没有整体失败。失败的是让静态 Skill 或固定子 Agent 阵容充当孵化总脑；把 Skill 用作边界明确的证据提取器是合适的。

第五版可以把用户有权提供的账号材料和视频自动转换为结构化账号证据。建议采用：

```text
授权账号材料
-> MediaKit 单视频感知
-> 受限语义提取 Skill
-> Schema 校验与确定性跨视频聚合
-> AccountEvidencePack
-> Lead 独立作出孵化判断
```

这条链可以显著减少人工抄录、转写和逐条归纳，但不能仅凭公开作品自动证明账号定位、真实粉丝画像、爆款原因或可复制策略。

## 第四版仓颉变种到底是什么

第四版在提交 `d2bbfecd` 引入了 MIT 许可的 Cangjie Skill 思路，来源版本为 `355dd47a97eeb87d249bf7d32aab561405b6de76`。其变种 `video-method-distillation` 面向长视频、课程、访谈和播客，核心是：

- 先理解完整来源与章节结构；
- 从框架、原则、案例、反例、术语五个视角抽取证据；
- 每条证据绑定时间范围、来源引用和内容哈希；
- 区分多个独立上下文，保存反例、限制和不确定性；
- 最后才把可复用方法编译成候选 Skill。

它不是账号拆解器，也不应原样迁移。可复用的是“完整来源、多视角、证据引用、反例和边界”五类语义；应丢弃方法 Skill 安装、固定数量资格、晋级和旧编译器。

第四版的 `video-pattern-learning` 与账号拆解更接近。它将单条视频分成：

1. 可观察事实；
2. 元素承担的内容功能；
3. 对受众意义的解释；
4. 可变化的适配变量；
5. 不可复制的表达资产。

第五版可吸收这个分层，但不能继承“固定一至三条视频”之类的产品规则。样本量应作为覆盖说明，而不是语义硬门。

## MediaKit 当前能提供什么

本机动态探测 `mediakit-cli 0.2.0` 的 `--schema`，没有发起付费任务：

| 能力 | 可直接取得 | 边界 |
| --- | --- | --- |
| `asr-subtitles` | 带时间戳语音、可选说话人与置信度 | 云端异步；输入需公网 URL |
| `video-ocr` | 带时间戳字幕和画面文字 | 云端异步；详细模式仍需真样本验收 |
| `segment-scenes` | 场景/转场边界 | 只说明画面变化，不等于语义段落、钩子或 CTA |
| `probe-video-metadata` | 时长、编码、分辨率、帧率等 | 只属于技术元信息 |
| `analyze-video-storyline` | 影视剧情片段和高光故事线 | 面向电影、电视剧，不默认用于通用达人账号 |
| `analyze-video-highlights` | 短剧或小游戏高光 | 领域限定，不是通用短视频爆点分析 |

因此 MediaKit 是眼睛和耳朵的一部分，不会直接输出“这个账号为什么成功”。通用短视频的内容主语、开场功能、表现形式、证明方式、商业露出和行动引导，仍需受控多模态模型根据 MediaKit 时间证据提取。

## 建议的结构化数据

### 账号与样本

- 平台、账号第一方标识、规范主页、展示名、简介、认证和采集时间；
- 作品样本的选择依据、时间窗口、可见总量、已取得量、遗漏原因和覆盖率；
- 每条作品的第一方标识、标题、文案、发布时间、公开指标、指标采集时间和来源哈希。

### 单条视频观察

- 时长、ASR、OCR、场景边界、人物/物体/环境、镜头与剪辑变化；
- 内容主语、观众所处问题或欲望、内容母题与具体题材；
- 表现形式，例如口播、微短剧、情景剧、Vlog、纯素材图文或混合形式；
- 开场、冲突、信息推进、证明、情绪变化、商品或服务露出、CTA；
- 每个推断的时间戳、证据引用、置信度、未知和替代解释。

### 跨视频账号模式

- 重复内容母题及其变化，不把一次题材写成账号规律；
- 表现形式分布、人物/关系结构、开场功能、证明方式、CTA 与商业连接；
- 发布时间、时长和公开指标的可复现分布；
- 支持作品、反例作品、时期变化、覆盖缺口和生产负担；
- 可迁移的“功能”及所需条件，不复制台词、角色、镜头、音乐和品牌识别。

所有字段必须区分 `observed / inferred / unknown`。推断字段必须能回指作品和时间证据，确定性代码只做计数、分布、交叉引用和 Schema 校验。

## 明确禁止自动生成的结论

- “这个账号的真实定位就是……”；
- “这就是它的粉丝画像”；
- “这条视频因为某个钩子所以爆了”；
- “照这个结构拍就会成功”；
- “这个模式一定适合当前用户”。

这些只能作为带反例和未知的假设交给 Lead。Lead 可以采用、修改或拒绝，账号提取器无孵化决策权。

## 数据来源边界

首版只处理用户上传、用户导出、用户授权访问或人工提供的作品清单。它不能把一个任意抖音主页 URL 自动扩展成批量爬虫；E14 已记录平台自动化采集限制。浏览器/MCP 未来只能在平台许可、用户授权和可见操作边界内补齐账号身份与作品清单，Cookie、LocalStorage 和临时媒体地址不得进入模型结果。

## 技术落法

- 第一阶段不需要向量数据库，也不需要微调模型；用版本化 JSON Schema、对象文件和现有持久化即可。
- MediaKit 任务保存输入哈希、动态 Schema 哈希、CLI 版本、执行模式、幂等令牌、任务回执、输出哈希和费用/云处理同意。
- 语义提取使用一个窄 Skill 或结构化模型调用；它只能读媒体证据并输出候选字段，不能读取孵化方法、修改项目事实或给最终方案。
- 聚合器必须是普通确定性代码。它只汇总同字段、保留反例和缺失，不调用第二套 Agent 运行时。
- 对 Lead 暴露一个高层只读入口，不把 ASR、OCR、轮询、下载和几十个底层媒体工具全部塞进模型上下文。

## 验收门槛

先在隔离分支用一个用户授权账号做小样本实验：

- 人工逐字段核对单视频观察的准确性和时间引用；
- 验证跨视频汇总没有把单条样本、相关性或缺失值升级成规律；
- 同时包含支持样本与反例，样本数量和覆盖只作为报告，不作为硬门；
- 比较“纯多模态模型”与“MediaKit 原子 + 受限提取器”，确认后者确实提高准确率、可追溯性或成本；
- Lead 使用与不使用证据包各回答一次，只有最终孵化判断得到可复核改善才考虑接入主线。

在真实样本通过前，本能力状态是 `reviewed / experiment proposed`，不是已交付账号拆解。
