# 第五版孵化内核执行手册

## 每个纵切的顺序

1. 先读业务合同、审计证据、旧版失败提交和当前代码。
2. 用真实业务案例写可观察的失败测试。
3. 运行测试，确认失败来自能力缺失。
4. 实现当前纵切的最少代码，不顺便扩展发布、媒体或前端。
5. 运行定向测试、相关回归、格式检查和敏感信息扫描。
6. 记录哪些只是代码合同，哪些经过真实模型、人工专家或真实业务结果验证。
7. 只有结果证据充分时才更新架构决定和产品状态。

## 判断类测试

- 测最终业务输出，不固定思考过程、工具顺序、提问轮数或工作阶段。
- 同一案例要测试新证据到来后的修订能力。
- 检查依据、未知、替代方案、表现形式、内容发动机、变现、转化和最小实验。
- 检查是否编造事实、承诺爆款、套人口刻板印象或复制对标表达。
- 模型裁判必须由人工专家样本校准；模型评分不能独自签署架构决定。

## 稀疏信息修正

- 区分“请求还能提供什么价值”和“当前证据是否足以承诺一条路线”。允许继续，不代表允许用假设补齐受众、表现形式和变现结论。
- 先用稀疏、信息充分、明确具体任务、拒绝继续回答和新增事实修订五类同组样本冻结失败，再改提示词或方法。
- 不使用关键词拦截、独立访谈 Agent、固定问卷、访谈状态机、强制 `tool_choice`、字段完整度或输出改写来修复模型判断。
- 验收最终回答是否有依据、是否保留条件和是否会据新事实修订；不固定问题文本、轮数和工具轨迹。

## 数据与记忆

- 用户事实、来源事实、推断、创意假设、未知、已批准决定和观察结果必须分开。
- 案例只有产生观察结果并经人工复核后才能进入记忆。
- 案例支持有效、争议、被替代和退役状态；检索必须保留反例和限制。
- 主体内学习先于跨主体学习，跨项目默认关闭。

## 完成等级

```text
designed -> tested -> model-evaluated -> expert-calibrated
         -> live-pilot -> outcome-observed -> adopted
```

自动测试只能证明合同和实现，不能证明 Agent 已经会孵化。至少完成个人、品牌、产品各一个真实的“判断、实验、结果、复盘、修正”闭环后，才可以声称内核通过业务验收。
